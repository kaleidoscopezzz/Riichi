# Riichi V1.0 需求基线草案

状态：F0-01、F0-02、F0-03 已正式验收；F0-04 赛事领域基础实现与自检，等待 Planner 源码审查。

## 产品定位与范围

基于 Web 的四人立直麻将赛事管理系统，采用前后端分离、模块化单体架构。V1.0 **仅支持个人赛**；微信群能力属于未来版本候选，不纳入当前范围。

## 已确认的 V1.0 核心需求

| 领域 | 已确认规则 |
| --- | --- |
| 系统账号 | 选手必须先注册系统账号。F0-02 提供注册、Session 登录退出和本人昵称管理。 |
| 参赛规模 | 每场赛事选择 4、8、12 或 16 名选手。 |
| 赛事轮数 | 每场赛事设置 1～6 轮。 |
| 麻将机 | 最多4台非 retired 物理设备，设备独立编号，退役保留历史实体。 |
| 第一轮 | 随机分桌，每桌 4 人。 |
| 后续轮次 | 按累计积分降序排列，每 4 名选手分配一桌。 |
| 成绩录入 | 管理员手动录入半庄最终点数。 |
| 计分配置 | 开局点数、返还原点、Uma 可配置。 |
| 默认配置 | 25000 点开局，30000 点返还，Uma 为 `[30, 10, -10, -30]`。 |
| Oka | `4 × (返还原点 - 开局点数) / 1000`，默认 `+20`，F0-04 精确推导，只读。实际半庄计分留待后续。 |
| 冠军 | 完成所有轮次后产生个人冠军，同分时的决胜规则待定。 |
| 领域设计 | Tournament 采用领域对象设计，各赛事实例独立；F0-01 不提前实现。 |

## F0-01 骨架交付范围

- Django/DRF 服务、清晰配置结构、环境变量、SQLite 本地开发、PostgreSQL 配置预留。
- `GET /api/v1/health/` 标准 JSON 健康检查，严格限定本地开发 CORS 来源。
- React/TypeScript/Vite 应用，使用 Tailwind、shadcn/ui 和 Lucide React。
- 左侧导航、顶部 Header、主内容、统一标题及面包屑，桌面优先并兼容手机。
- 仪表盘、赛事管理、选手管理、麻将机管理、系统设置五个基础页面。
- 仪表盘展示欢迎信息、功能入口、基础信息与真实后端连接状态；其他业务页面使用统一空状态，不填充虚构业务数据。
- Riichi Premium 视觉规范：深海军蓝、石墨黑、中性色为基础，适度金色或青绿色；默认暗色，预留亮色主题能力。
- 基础自动化测试、构建、浏览器与 API 联调验证，以及运行与工程文档。

## F0-02 已实现范围（已验收）

- 唯一用户名登录，Django 密码散列及四项官方密码强度校验；注册确认密码，普通账号不具备管理员权限。
- accounts.User 身份与 players.PlayerProfile 一对一分离；昵称独立于用户名，包含创建/更新时间，注册原子建立档案。
- Session Cookie 登录、退出和刷新恢复；写请求 CSRF，健康接口继续匿名可访问。
- 本人可查询和修改昵称；管理员可按昵称/用户名搜索分页选手列表（每页20项），普通用户无列表权限。
- 前端独立登录/注册页、个人资料、真实选手列表、路由保护和角色菜单，无演示业务数据。
- 不含头像、战绩、段位、战队、微信、找回密码、邮件验证及公网登录限流；这些不因本次实现成为 V1.0 新承诺。

## F0-03 设备资源台账（已验收）

- 管理员可新增、查看、编辑设备资料及非退役状态、确认退役。普通用户与匿名用户不具备查询或修改能力。
- 稳定id与业务machine_no分开；业务编号输入1～3位ASCII数字并规范化为三位（000～999），不限制为001～004。现役设备编号唯一；退役后可复用业务编号，新物理设备必须获得新ID。
- 状态为available、maintenance、disabled、retired。前三者均计入4台现役上限；retired不占容量，但只读保留历史，不能通过普通API恢复或删除。
- 设备字段包含名称（必填）、位置和备注（可选）、创建/更新时间。按编号排序，可按编号/名称搜索、按状态筛选，分页查看包括已退役设备。
- 总览统计来自后端真实数据，搜索/筛选不改变全局现役统计含义；容量满时禁用新增并解释释放规则。
- available只满足未来参与分配的设备状态条件，不表示当前无赛事占用；本阶段没有轮次、对局、资源调度或跨赛事占用锁。

## F0-04 Tournament 领域基础（已实现，待验收）

- 管理员创建/查询/搜索/分页赛事，草稿可分步编辑；配置与名单可用单个请求原子保存。
- 每场独立持久化名称、说明、1～6轮、开局/返还点数、四项 Uma、创建者和时间。默认25000/30000、[30,10,-10,-30]；Oka只读推导，无全局赛事状态。
- 点数输入正整数；存储兼容上限2147483647。Uma为恰好四项整数或精确十进制字符串，单项最多64字符；不限制总和、正负或顺序大小。上述存储边界是工程限制，不代表已批准的赛制限制，其他数值规则仍待Planner确认。
- 名单关联真实 PlayerProfile，最多16人，不重复、不接受不存在或已停用账号；有效管理员档案同样有资格。草稿允许0～16人，启动仅允许4/8/12/16人。
- 启动事务重新校验并保存昵称快照，设置started_at；仅draft→started，已启动规则与名单冻结，重复启动冲突，无取消/删除/恢复/完赛API。
- 预计每轮桌数仅在合法人数下返回1～4，其余草稿返回null；不检查设备是否可调度，不创建Round、RoundTable或MachineAllocation，不锁定物理设备。
- 管理页、全部赛事API限管理员Session；所有写操作CSRF保护、严格字段白名单。普通用户与匿名用户不能管理。
