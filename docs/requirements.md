# Riichi V1.0 需求基线草案

状态：产品范围已经确认；工程首次 Git 基线**尚未建立**。当前执行 F0-01，仅建设工程骨架，不实现以下赛事业务。

## 产品定位与范围

基于 Web 的四人立直麻将赛事管理系统，采用前后端分离、模块化单体架构。V1.0 **仅支持个人赛**；微信群能力属于未来版本候选，不纳入当前范围。

## 已确认的 V1.0 核心需求

| 领域 | 已确认规则 |
| --- | --- |
| 系统账号 | 选手必须先注册系统账号。注册与认证将在后续任务实现。 |
| 参赛规模 | 每场赛事选择 4、8、12 或 16 名选手。 |
| 赛事轮数 | 每场赛事设置 1～6 轮。 |
| 麻将机 | 最多 4 台，设备独立编号。 |
| 第一轮 | 随机分桌，每桌 4 人。 |
| 后续轮次 | 按累计积分降序排列，每 4 名选手分配一桌。 |
| 成绩录入 | 管理员手动录入半庄最终点数。 |
| 计分配置 | 开局点数、返还原点、Uma 可配置。 |
| 默认配置 | 25000 点开局，30000 点返还，Uma 为 `[30, 10, -10, -30]`。 |
| Oka | 由开局点数和返还原点自动计算，默认值为 `+20`。具体算法将在后续计分任务实现。 |
| 冠军 | 完成所有轮次后产生个人冠军，同分时的决胜规则待定。 |
| 领域设计 | Tournament 采用领域对象设计，各赛事实例独立；F0-01 不提前实现。 |

## F0-01 骨架交付范围

- Django/DRF 服务、清晰配置结构、环境变量、SQLite 本地开发、PostgreSQL 配置预留。
- `GET /api/v1/health/` 标准 JSON 健康检查，严格限定本地开发 CORS 来源。
- React/TypeScript/Vite 应用，使用 Tailwind、shadcn/ui 和 Lucide React。
- 左侧导航、顶部 Header、主内容、统一标题及面包屑，桌面优先并兼容手机。
- 仪表盘、赛事管理、选手管理、麻将机管理、系统设置五个基础页面。
- 仪表盘展示欢迎信息、功能入口、基础信息与真实后端连接状态；其他业务页面使用统一空状态，不填充虚构业务数据。
- Riichi Premium 视觉规范：深海军蓝、石墨黑、中性色为基础，适度金色或青绿色；默认暗色，预留亮色主题能力。
- 基础自动化测试、构建、浏览器与 API 联调验证，以及运行与工程文档。

## TBD 与实现边界

| 未决事项 | 当前处理 |
| --- | --- |
| 半庄终局同点时的顺位 | 等待 Planner 明确，不能擅自采用座次、优先权等规则。 |
| 最终累计积分同分时的冠军决胜 | 等待 Planner 明确，不自动指定加赛或其他决胜办法。 |
| 其他尚未明确的异常业务流程 | 随后续任务梳理并确认，不推断成已批准需求。 |

业务规则发生变化时，先明确 Planner 决策再更新本文和对应验收标准。本任务不实现创建赛事、注册登录、选手管理、分桌、计分、瑞士轮等业务功能；页面入口和占位不代表功能已实现。

## 未来版本候选

微信群赛事发布、报名、账号绑定和赛事播报。候选项不构成 V1.0 承诺，未获得独立任务前不增加微信 SDK、回调、身份绑定或消息发送模块。
