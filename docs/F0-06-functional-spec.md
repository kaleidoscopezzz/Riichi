## 2. 目标完整流程

1. 创建赛事草稿，选择真实参赛档案，配置轮数、点数、Uma、头名赏Oka与预设计分策略。
2. 管理员启动赛事，原子校验并冻结规则、版本、名单及昵称快照。
3. 首轮生成前选择本场使用的1～4张真实物理桌，查看并确认赛事逻辑桌A～D与物理桌映射；选桌数必须等于人数/4。
4. 原子取得赛事级物理桌占用并生成第一轮随机四风座次；已有F0-05首轮按兼容流程接续，不能重排覆盖。
5. 管理员逐桌录入四人原始终局点数，保存草稿、修正、正式确认；只有确认结果进入正式积分。
6. 当前轮全部桌次确认后，按第9节完整排序生成下一轮，重新分组并随机安排东南西北，沿用本赛事物理桌映射。
7. 重复至配置的最后一轮，按冻结冠军规则计算最终顺序；若仍完全并列，等待公开抽签及管理员确认记录。
8. 原子正式完赛，保存唯一冠军、最终排名与结果版本，自动释放本赛事全部物理桌占用。完赛结果只读查询，策略升级不得静默重算。

日常换轮不要求管理员释放再分配设备。取消、提前完赛、强制中断、任意回滚已确认成绩、复杂罚分与异常恢复不在本次已确认范围。

## 4. 半庄成绩录入与确认

每个RoundTable仅有一份当前成绩记录，关联该桌既有四个RoundSeat/TournamentParticipant，不能通过成绩请求换人或换座。四人的正式原始点数均为整数，**允许负数与零**；拒绝布尔、浮点、重复选手、其他桌/赛事选手、不完整成绩和未知字段。终局点数不沿用开局/返还参数的正数限制。

成绩草稿可保存尚未填完的表单；所有已提供值也须合法。正式确认必须四人完整、身份集合完全匹配，并通过总点数政策。相同桌不能通过重复POST创建第二份成绩，保存/确认须有并发或版本冲突防护，不能把盲目重试当成第二次确认。

确认事务保存原始点数、并列名次、基础积分、Uma/Oka顺位奖励、最终单场积分、冻结策略标识/版本、录入和确认管理员及时间。进行中已确认成绩可通过显式更正入口修改，不能以保存草稿或重复确认直接覆盖；完赛后全部成绩仍只读。

更正允许任意已有轮次，不因后续轮次已开始或录入成绩而关闭。更正必须完整提交本桌四人的整数点数、保持总和等于四倍开局，并提供当前成绩版本；版本已变化返回409，管理员载入最新值后核对重填，不自动重试。更正一次保存即更新正式积分，保留confirmed状态；同一事务递增版本并保存前后原始点数、精确积分、规则与编辑/确认信息快照，以及更正人、时间和可选说明。未改变数值的保存不增加成绩版本或更正记录。

更正重算该桌积分及全赛事累计总分、第一/第二次数和逐轮指标；既有轮次、四风、参赛者和物理桌快照不覆盖，后续尚未生成的轮次使用最新累计表现。原始成绩留档，不删除历史，也不回退其他桌的确认状态。历史未确认成绩在赛事进行中同样可继续录入，即使旧数据已存在后续轮次。

输入时使用冻结规则进行只读Fraction试算，返回原始点数、基础分、顺位奖励和本场积分；未填写完整时仅能试算已填部分的基础分，合计异常仍可看到完整试算，但不得确认或保存更正。试算不创建成绩、修改版本、记录审计或计入排名；前端取消旧请求并核对输入，迟到或乱序响应不能显示在新数字下。

## 5. TBD-001：RESOLVED / split_rank_bonus_v1

同一半庄终局原始点数相同的选手并列占据对应名次，平均分配其覆盖名次的**全部顺位奖励（Uma与第一名Oka）**，不采用座次、报名顺序或账号ID优先。

定义四个名次奖励`B = [uma[0]+oka, uma[1], uma[2], uma[3]]`。自动推导时`oka = 4*(return_points-starting_points)/1000`；自定义时`oka`直接使用本赛事保存的非负精确值，`0`表示无头名赏。按原始点数降序识别并列组，组从第r名起（r从1计）、共k人，则组内每人获得`sum(B[r-1:r-1+k])/k`。自定义Oka同样参与第一名并列组的均分，不独占给某个选手。

`单场积分 = (终局点数-return_points)/1000 + 分配的顺位奖励`。

新赛事选高高碰并配置桌附加分时，后续轮次增加该桌每人的冻结附加基础分：`单场积分 = (终局点数-return_points)/1000 + 本桌附加基础分 + 分配的顺位奖励`。采用独立策略标识`add_table_base_bonus_v1`，原Uma/Oka同点策略含义保持；同桌四人均加同一值，开局/返还原点和原始总点数要求不变。通用积分总和因此增加`4 × 本桌附加基础分`，不强制零和。

默认参数的**顺位奖励**示例（不是完整单场积分）：

| 同点情况 | 顺位奖励，一至四个排列位置 |
| --- | --- |
| 无并列 | 50、10、-10、-30 |
| 两人并列第一 | 30、30、-10、-30 |
| 两人并列第二 | 50、0、0、-30 |
| 两人并列第三 | 50、10、-20、-20 |
| 四人全部同点 | 5、5、5、5 |
| 三人并列第一 | 50/3、50/3、50/3、-30 |
| 三人并列第二 | 50、-10、-10、-10 |
| 两组分别并列第一、第三 | 30、30、-20、-20 |

共享名次用并列组起始名次表示，如1、1、3、4或1、2、2、4；“并列第一次数”只增加第一次数，不因覆盖第二位置再增加第二次数。此为并列组名次的表达，不使用隐藏座次打散并列。

通用总分之和为`(四人终局点数总和-4*return_points)/1000 + sum(uma) + oka`。自动推导时等价于原公式`(四人终局点数总和-4*starting_points)/1000 + sum(uma)`。只有相应条件满足时才为零和；自定义Oka或非零和Uma不得被强制修正为零和。

例如25000开局、30000返还、默认Uma，终局40000/30000/20000/10000：Oka=0时积分为40/10/−20/−50，合计−20；Oka=12.5时积分为52.5/10/−20/−50，合计−7.5。无头名赏不取消Uma，不改变基础积分公式，也不放宽终局总点数必须等于四倍开局的确认校验。

### 精确有理数权威计算与存储（已确认）

**OP-05：RESOLVED**。采用Python Fraction等精确有理数机制完成后端权威计分、累计与排名。原始整数及配置的十进制字符串可通过字符串或Decimal精确解析为有理数，禁止先经过float；Oka、同点均分、单场积分、累计积分与比较全过程保持精确有理数，不能先做有限精度除法再转换。

三人并列的`50/3`等循环小数须无损保留；持久化使用规范化整数分子/正整数分母或等价无损表示，大整数可存十进制字符串，确保SQLite/PostgreSQL及JSON传输不转成浮点。具体字段名称在实现中确定，不再采用先将权威积分舍入为Decimal小数的方案。

读取无损值后按有理数比较，不能按分数字符串、仅按分子或按展示小数排序。前端可近似展示并提供精确值说明，但近似值不参与任何并列、累计、分桌或冠军判定；禁止浮点累计。F0-06候选已采用规范化分子/分母字符串JSON持久化，实际结果以交付报告为准。

## 6. TBD-002：RESOLVED / performance_v1

完成全部指定轮次后，依次比较：

1. 累计总积分降序（全部已确认单场积分的精确和）。
2. 第一名次数降序，并列第一也计一次。
3. 第二名次数降序，并列第二也计一次。
4. 最后一轮单场积分降序。
5. 仍同则依次比较倒数第二轮、倒数第三轮，直到第一轮。
6. 所有指标仍完全相同，对该并列组公开抽签，管理员确认并记录过程及结果。

不能用账号ID、座次、登记顺序作为隐藏的最终决胜项。**首轮持久化随机排列顺序只用于后续分桌的完全同分兜底，不适用于冠军或最终名次决胜**；最终全部指标仍同必须公开抽签。待抽签不是已完赛，不能先保存临时冠军冒充最终冠军。

抽签须有明确入口，展示并列组选手及已相同指标。设计建议：管理员记录公开抽签方式、过程说明、抽签时间和该组完整结果顺序，再二次确认；系统校验结果恰好覆盖该组且无重复，记录操作者/确认时间/规则版本/结果。不能由后台静默随机，也不能因刷新自动重抽；涉及最终排序的全部未决并列组均须处理。未确认记录不能用于完赛。

**审查修复补充（Owner已在项目约束明确确认，PR #2已实现）**：同一并列组在同一来源成绩版本下，同时只能存在一条待确认记录，不能先录多份结果再挑选其一确认。待确认记录录入有误时，管理员须填写原因将其作废；作废记录连同作废人、时间与原因永久保留并可查询，之后才能重新录入。已确认记录不可作废，完赛后全部抽签记录只读。

成绩更正使来源成绩版本变化时，旧抽签记录保留原文，不能用于当前排名，也不伪造作废审计；原已确认记录仍不可作废。当前成绩仍需抽签时，按新的来源版本重新记录并确认公开抽签，现有单组单条待确认限制照常适用。完赛快照仅引用真正用于当前排名的抽签ID，所有历史记录另可查询。

## 7. 规则配置与版本

```json
{
  "score_tie_policy": "split_rank_bonus_v1",
  "champion_tiebreak_policy": "performance_v1",
  "rules_version": 2,
  "oka_override": null
}
```

每场独立保存数字参数、策略标识和版本，后续分桌排序规则同样纳入冻结版本。草稿可修改已支持配置，第一版策略选项仅已确认预设；不接受任意函数、表达式或动态代码。启动后冻结，后端注册表按标识/版本分派；新增策略必须用新标识或版本，不能改旧策略含义。未知版本明确拒绝计算，不回退到“最新”。

Oka配置扩展采用`rules_version=2`，同点及冠军策略标识保持不变。`oka_override=null`为自动推导，`"0"`为明确无头名赏，其余接受非负整数或最多64字符的精确十进制字符串（不接受布尔、JSON浮点、负数、空串、科学计数法、NaN或Infinity）；写入后以字符串保存。省略此字段的新赛事默认自动推导；PATCH省略该字段保持原值，显式null恢复自动推导。API的`oka`仍为只读的实际生效值。

既有赛事保持`rules_version=1`及原规则来源，版本1只允许自动推导，包含原先支持的零值、小数及负推导值。新赛事默认版本2；旧草稿明确配置自定义Oka时原子升级到版本2并记录`draft_configured_v2`来源，单纯读取、启动或修改其他字段不自动升级；若请求显式指定版本1及自定义Oka则拒绝。恢复自动推导不会自动降级版本。启动后两种模式和值均冻结，成绩、后续分桌与完赛的版本2规则快照保存配置值及实际生效Oka，旧快照不改写、不重新计算。

F0-06的0003/0004首次引入规则字段时，为历史赛事回填可追溯的版本1，并保留赋值来源/时间/迁移版本，不伪造历史管理员当时选择；本次0007不修改这些历史版本或来源。不得修改原开局点数、返还原点、Uma、名单、昵称快照或已生成分桌；历史回填不等于已有成绩已计算。已启动赛事仍不能普通编辑规则；采用兼容流程接入新资源模式与规则字段的来源说明单独审计。

确认成绩保存策略与计算输入/精确结果，完赛保存最终排名及冠军快照；之后规则升级不自动改写历史结果。

预览只读，确认使用绑定管理员/赛事/轮次/冻结名单/规则/成绩版本的签名计划。并发变化拒绝旧计划，不自动重放。手动触屏可在边缘自动滚动到视口外桌位，键盘有统一Select交换入口。附加分在轮桌生成时固定，试算/确认/更正/累计/冠军均保留同一值；前轮更正不改已生成分桌或桌附加分。

- 第一轮沿用F0-05真实结果；新赛事首轮仍随机生成并固定，不覆盖旧RoundTable/RoundSeat。
- 仅能生成紧接当前轮的下一轮，轮号不超过配置1～6；前一轮所有预期桌的四人成绩必须确认，缺桌、缺人或草稿均拒绝。
- 历史赛事及新高高碰按截至前一轮的已确认累计积分、第一名次数、第二名次数依次降序，仍同则按最近已确认轮、倒数第二轮等逆序逐轮积分降序，全部相同按首轮持久化随机排列顺序先后；每连续四人构成一桌。历史模式允许重复对手，其含义保持。

**OP-02：RESOLVED**。不再对累计同分组额外重新抽序。首轮生成时保存完整的参赛者随机排列顺序；旧F0-05数据按首轮已持久化的逻辑桌号升序、每桌东南西北顺序还原原始随机序列，记录来源与校验结果，不重新随机、不使用账号或座次记录ID排序。如果旧序列缺失或不完整，进入兼容复核，不凭空补造。排序输入、来源成绩版本、首轮序列引用及新轮风位结果均可审计；该兜底仅用于分桌，冠军全同仍公开抽签。

### 9.1 清楚的成绩明细与统计

累计积分、各轮基础积分、Uma/Oka顺位奖励和本轮积分优先展示两位小数；精确有理数可展开，不参与前端排序或累计。逐轮明细显示轮次、逻辑桌、终局点数、当桌共享名次及积分拆分。“当桌最高分”指本桌原始终局点数最高，可并列。

本场亮点展示四位回避率最高、单个半庄最高终局点数、当桌第一次数最多（吃1）。仅采用已确认成绩，包含已淘汰人员已打完的半庄，领先者并列时全部展示。终局点数是半庄结束的点棒，系统没有和牌累计打点数据，不将其冒称和牌统计。

四位回避率＝（已确认半庄数－共享名次为第4的次数）÷已确认半庄数；无样本为空。同点沿用权威共享名次，故并列第三不计第四，并列第一均计吃1。百分比采用Fraction无损存储，前端仅展示近似百分比，样本数在选手行展示。既有最简完赛快照若没有逐轮数据则统计为空，不补造历史统计或改写完赛分数。

### 9.2 每轮可选淘汰

- 当前及此前已生成轮次的所有桌成绩均确认、下一轮尚未生成、有剩余配置轮次且仍在赛人数大于4时，可选择预览淘汰累计排名末四人。旧轮次尚缺成绩时先补齐，不按不完整累计排名淘汰。直接生成下一轮表示本轮不淘汰；没有固定起始轮、自动淘汰或提前缩短赛程。
- 每轮最多确认一次、恰好四人，始终至少保留四人。确认后，下一轮只安排剩余人员；最后四人打完所有剩余配置轮次。初始参赛关系、首轮随机序列、历史座次和成绩不删除。
- 末四人依据`performance_v1`完整累计表现比较。完全并列组横跨晋级/淘汰边界时须记录公开抽签并二次确认，顺序靠前者优先晋级；抽签后另行预览、确认淘汰。完全并列组若全部晋级或全部淘汰，不为这一边界额外抽签。禁止用ID、昵称或首轮随机顺序决定淘汰人选。
- 保存EliminationRecord：轮次、四个稳定participant ID、来源成绩与资格状态、确认时排名、所用抽签、管理员及时间。资格在TournamentParticipant另记淘汰轮次；不归档PlayerProfile或停用User。
- 淘汰后逻辑桌使用A～当前桌数，原A～D与全部关联历史保留，多余桌位的关联留痕结束，可将其可用设备故障替换到仍使用的桌位。高高碰附加分仍按实际使用的逻辑桌配置；不用的桌位配置和设备状态不阻止剩余人员开下一轮。
- 后续更正旧成绩更新积分与统计，不自动恢复已淘汰资格，不撤销淘汰审计或覆盖已生成轮次。排名先显示仍在赛者，再按淘汰轮次从晚到早；同阶段继续用原表现比较，最终完全并列仍公开抽签。冠军从完成剩余赛程者中产生。
- 淘汰边界抽签带用途与指定轮次，最终名次抽签单独处理；完整成绩版本及资格来源必须匹配，旧记录保留但不跨用途复用。淘汰、下一轮生成、更正和完赛共享原写锁，过期名单/来源拒绝且不自动重放。

## 10. 完赛事务与异常防护

建议管理员点击“正式完赛”，确认前显示：指定轮次全部存在、各桌成绩全部确认、全部最终并列已按performance_v1解决、冠军唯一、将自动释放哪些物理桌。
