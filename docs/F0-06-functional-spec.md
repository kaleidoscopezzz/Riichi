## 1. 定位、范围与规则来源

Riichi是**轻量级四人立直麻将个人赛事管理系统**，服务麻将馆管理员快速组织比赛。物理桌是必要资源，不把设备调度作为产品主线。

已确认：选手由雀庄管理员维护PlayerProfile，内部User只作技术兼容，选手无需注册/登录（UAT-FIX-01批准变更）；每场4/8/12/16人、1～6轮；开局点数、返还原点、四项Uma按赛事保存；默认25000、30000、[30,10,-10,-30]，Oka推导为20。无团队赛、微信、任意公式编辑器或动态表达式执行。

以下业务规则包含D0-01原任务与Planner本轮五项最终决策，均以本规范为准。剩余实体/字段/API命名等“设计建议”属于实现选择，不改变已确认规则；最终实现名称和验证见交付报告。TBD-001/002和本轮OP-01～OP-05决策均已关闭，不再保留互斥候选方案。

## 2. 目标完整流程

1. 创建赛事草稿，选择真实参赛档案，配置轮数、点数、Uma与预设计分策略。
2. 管理员启动赛事，原子校验并冻结规则、版本、名单及昵称快照。
3. 首轮生成前选择本场使用的1～4张真实物理桌，查看并确认赛事逻辑桌A～D与物理桌映射；选桌数必须等于人数/4。
4. 原子取得赛事级物理桌占用并生成第一轮随机四风座次；已有F0-05首轮按兼容流程接续，不能重排覆盖。
5. 管理员逐桌录入四人原始终局点数，保存草稿、修正、正式确认；只有确认结果进入正式积分。
6. 当前轮全部桌次确认后，按第9节完整排序生成下一轮，重新分组并随机安排东南西北，沿用本赛事物理桌映射。
7. 重复至配置的最后一轮，按冻结冠军规则计算最终顺序；若仍完全并列，等待公开抽签及管理员确认记录。
8. 原子正式完赛，保存唯一冠军、最终排名与结果版本，自动释放本赛事全部物理桌占用。完赛结果只读查询，策略升级不得静默重算。

日常换轮不要求管理员释放再分配设备。取消、提前完赛、强制中断、任意回滚已确认成绩、复杂罚分与异常恢复不在本次已确认范围。

## 3. 物理桌与赛事固定映射（已确认目标）

- 店内可登记5张或更多物理桌，解除当前最多4台非退役设备的capacity_slot容量限制；单场仍最多使用4张。
- 保留稳定machineId。界面可称“物理麻将桌”，不为改名另建身份实体，也不按编号关联历史。
- 逻辑桌A/B/C/D是赛事内稳定桌位，RoundTable仍是某一轮的桌次；不同轮次选手和四风变化，默认物理桌不变。
- 必须显式选择并确认本场物理桌；新模式不得无提示沿用F0-05“从全池自动选前几台”的日常流程。初始映射的设计建议：按所选设备编号升序预览A～D，由管理员确认，保存实际映射。
- 同一物理桌任一时刻只允许一场赛事持有有效占用；available仅表示设备状态，不等于未占用。不得只检查前端状态或count后再写入。
- 故障允许简化替换：管理员选择未占用、状态可用的新物理桌并确认原因，原子结束旧预留、建立新预留，逻辑桌字母保持，后续轮次沿用替换后的映射。不得改写过去轮次的映射快照或座次。
- 保留F0-05调整/释放历史。旧“单轮手动释放”接口不能成为新模式的换轮前置步骤，也不能绕过赛事预留释放他场资源；兼容细节见[架构迁移方案](architecture.md#兼容与迁移已实现qa验证)。

兼容规则已确认：F0-04已启动未分桌赛事进入新选桌/首轮流程；F0-05已有分桌保留原结果，原占用全部有效时继承固定桌位，已释放或异常占用需要管理员复核。不得重排首轮或破坏历史，新旧资源占用统一互斥。

## 4. 半庄成绩录入与确认

每个RoundTable仅有一份当前成绩记录，关联该桌既有四个RoundSeat/TournamentParticipant，不能通过成绩请求换人或换座。四人的正式原始点数均为整数，**允许负数与零**；拒绝布尔、浮点、重复选手、其他桌/赛事选手、不完整成绩和未知字段。终局点数不沿用开局/返还参数的正数限制。

成绩草稿可保存尚未填完的表单；所有已提供值也须合法。正式确认必须四人完整、身份集合完全匹配，并通过总点数政策。相同桌不能通过重复POST创建第二份成绩，保存/确认须有并发或版本冲突防护，不能把盲目重试当成第二次确认。

确认事务保存原始点数、并列名次、基础积分、Uma/Oka顺位奖励、最终单场积分、冻结策略标识/版本、录入和确认管理员及时间。确认后锁定；更正已确认成绩不自动开放，不能静默覆盖后续轮次或已发布冠军。

### 总点数与异常边界（已确认）

正式确认时四人点数总和**必须等于**`4 × 本赛事starting_points`，不是所有赛事固定100000。系统必须明确展示实录总和、应有总和及差值，不得偷偷补点、归零或均摊差额。

**OP-01：RESOLVED**。总和异常或尚未填完整可以保存草稿，但不得正式确认、计入正式积分或据此生成下一轮。没有“跳过校验”“强制确认”或异常罚分补正规则。实现所用有符号整数存储须无损表示输入，超出工程表示范围时明确报错，不能溢出、截断或转浮点。

## 5. TBD-001：RESOLVED / split_rank_bonus_v1

同一半庄终局原始点数相同的选手并列占据对应名次，平均分配其覆盖名次的**全部顺位奖励（Uma与第一名Oka）**，不采用座次、报名顺序或账号ID优先。

定义四个名次奖励`B = [uma[0]+oka, uma[1], uma[2], uma[3]]`，其中`oka = 4*(return_points-starting_points)/1000`。按原始点数降序识别并列组，组从第r名起（r从1计）、共k人，则组内每人获得`sum(B[r-1:r-1+k])/k`。

`单场积分 = (终局点数-return_points)/1000 + 分配的顺位奖励`。

默认参数的**顺位奖励**示例（不是完整单场积分）：

| 同点情况 | 顺位奖励，一至四个排列位置 |
| --- | --- |
| 无并列 | 50、10、-10、-30 |
| 两人并列第一 | 30、30、-10、-30 |
| 两人并列第二 | 50、0、0、-30 |
| 两人并列第三 | 50、10、-20、-20 |
| 四人全部同点 | 5、5、5、5 |
| 三人并列第一 | 50/3、50/3、50/3、-30 |
| 三人并列第二 | 50、-10、-10、-10 |
| 两组分别并列第一、第三 | 30、30、-20、-20 |

共享名次用并列组起始名次表示，如1、1、3、4或1、2、2、4；“并列第一次数”只增加第一次数，不因覆盖第二位置再增加第二次数。此为并列组名次的表达，不使用隐藏座次打散并列。

总分之和为`(四人终局点数总和-4*starting_points)/1000 + sum(uma)`。只有点数总和等于四倍开局且Uma总和为零等条件满足时才为零和；自定义非零和Uma不得被强制修正为零和。

### 精确有理数权威计算与存储（已确认）

**OP-05：RESOLVED**。采用Python Fraction等精确有理数机制完成后端权威计分、累计与排名。原始整数及配置的十进制字符串可通过字符串或Decimal精确解析为有理数，禁止先经过float；Oka、同点均分、单场积分、累计积分与比较全过程保持精确有理数，不能先做有限精度除法再转换。

三人并列的`50/3`等循环小数须无损保留；持久化使用规范化整数分子/正整数分母或等价无损表示，大整数可存十进制字符串，确保SQLite/PostgreSQL及JSON传输不转成浮点。具体字段名称在实现中确定，不再采用先将权威积分舍入为Decimal小数的方案。

读取无损值后按有理数比较，不能按分数字符串、仅按分子或按展示小数排序。前端可近似展示并提供精确值说明，但近似值不参与任何并列、累计、分桌或冠军判定；禁止浮点累计。F0-06候选已采用规范化分子/分母字符串JSON持久化，实际结果以交付报告为准。

## 6. TBD-002：RESOLVED / performance_v1

完成全部指定轮次后，依次比较：

1. 累计总积分降序（全部已确认单场积分的精确和）。
2. 第一名次数降序，并列第一也计一次。
3. 第二名次数降序，并列第二也计一次。
4. 最后一轮单场积分降序。
5. 仍同则依次比较倒数第二轮、倒数第三轮，直到第一轮。
6. 所有指标仍完全相同，对该并列组公开抽签，管理员确认并记录过程及结果。

不能用账号ID、座次、登记顺序作为隐藏的最终决胜项。**首轮持久化随机排列顺序只用于后续分桌的完全同分兜底，不适用于冠军或最终名次决胜**；最终全部指标仍同必须公开抽签。待抽签不是已完赛，不能先保存临时冠军冒充最终冠军。

抽签须有明确入口，展示并列组选手及已相同指标。设计建议：管理员记录公开抽签方式、过程说明、抽签时间和该组完整结果顺序，再二次确认；系统校验结果恰好覆盖该组且无重复，记录操作者/确认时间/规则版本/结果。不能由后台静默随机，也不能因刷新自动重抽；涉及最终排序的全部未决并列组均须处理。未确认记录不能用于完赛。

**审查修复补充（待Owner/Planner确认）**：同一并列组在同一来源成绩版本下，同时只能存在一条待确认记录，不能先录多份结果再挑选其一确认。待确认记录录入有误时，管理员须填写原因将其作废；作废记录连同作废人、时间与原因永久保留并可查询，之后才能重新录入。已确认记录不可作废，完赛后全部抽签记录只读。

## 7. 规则配置与版本

```json
{
  "score_tie_policy": "split_rank_bonus_v1",
  "champion_tiebreak_policy": "performance_v1",
  "rules_version": 1
}
```

每场独立保存数字参数、策略标识和版本，后续分桌排序规则同样纳入冻结版本。草稿可修改已支持配置，第一版策略选项仅已确认预设；不接受任意函数、表达式或动态代码。启动后冻结，后端注册表按标识/版本分派；新增策略必须用新标识或版本，不能改旧策略含义。未知版本明确拒绝计算，不回退到“最新”。

历史赛事新增字段时赋予可追溯的上述默认版本，保留赋值来源/时间/迁移版本，不伪造历史管理员当时选择。不得修改原开局点数、返还原点、Uma、名单、昵称快照或已生成分桌；回填不等于已有成绩已计算。已启动赛事仍不能普通编辑规则；采用兼容流程接入新资源模式与规则字段的来源说明单独审计。

确认成绩保存策略与计算输入/精确结果，完赛保存最终排名及冠军快照；之后规则升级不自动改写历史结果。

## 8. 累计积分与排行榜

只累计正式确认的成绩；草稿不进入官方排行。展示每位选手每轮原始点数、共享名次、奖励及单场积分、累计积分、已确认轮数和第一/第二次数。未完赛榜须标为实时/暂列，不能宣称官方最终冠军。

后续分桌按已确认累计积分、第一名次数、第二名次数、从最近已确认轮向前的逐轮积分排序，完全相同才使用首轮持久化随机排列顺序，详见第9节。最终排名按第6节在全指标相同时公开抽签，不能套用分桌兜底；所有积分比较均使用无损有理数。

## 9. 后续轮次

- 第一轮沿用F0-05真实结果；新赛事首轮仍随机生成并固定，不覆盖旧RoundTable/RoundSeat。
- 仅能生成紧接当前轮的下一轮，轮号不超过配置1～6；前一轮所有预期桌的四人成绩必须确认，缺桌、缺人或草稿均拒绝。
- 按截至前一轮的已确认累计积分、第一名次数、第二名次数依次降序，仍同则按最近已确认轮、倒数第二轮等逆序逐轮积分降序，全部相同按首轮持久化随机排列顺序先后；每连续四人构成一桌。允许重复对手，不引入避重、晋级或其他赛制。

- 逻辑桌A～D映射到赛事已选物理桌；不重新从全池挑设备、不每轮释放。生成、座次及结果版本关联原子写入，重复请求不能覆盖。

## 10. 完赛事务与异常防护

建议管理员点击“正式完赛”，确认前显示：指定轮次全部存在、各桌成绩全部确认、全部最终并列已按performance_v1解决、冠军唯一、将自动释放哪些物理桌。

一个事务重新验证以上条件，固定最终排行/冠军/规则版本/计算输入版本/抽签引用，记录完赛管理员与时间，将赛事写为目标completed状态，释放属于该赛事的全部有效预留，并按兼容策略结束相关旧active分配。任一步失败整体回滚，不能出现已完赛却无冠军、部分资源泄漏或释放了他场资源。

重复确认、重复生成、重复完赛、过期表单及同时写入须返回清晰冲突；不得自动重放不确定写入。成绩确认与下一轮生成必须使用共同赛事写入序列保护，避免读到尚未提交/已变更的积分。完赛和故障换桌使用共同物理桌锁及预留唯一约束，锁顺序在架构文档统一。
